## Key Data Decisions and Considerations

1. Target layout — the sibling's shape at this repo's scale:
   ```
   pyproject.toml                      # non-installable workspace root: pin, dev deps, ruff/mypy
   packages/mcp_db_server/             # the engine: one installable package
     pyproject.toml                    # deps, console scripts mcp-db-server / data-val-search-equivalence
     src/mcp_db_server/{server,validators,logconfig}.py
     src/mcp_db_server/data_validation/data_val_search_equivalence.py
     tests/
   instances/policy_db/                # config-only: .env, .env.example, config/, logs/, data/
   instances/metadata_db/              # config-only: .env, .env.example, logs/
   .mcp.json                           # stays at root (decision 15)
   README.md  MAINTAINING.server.md  MAINTAINING.instance.{policy_db,metadata_db}.md
   docs/{activities,code_review}/      # dated work records, unchanged
   ```
2. One package, not a multi-package mirror — the sibling's five packages earn their boundaries (five stages, mutual independence enforced by the build, 40 `sys.path.insert` lines deleted). This repo has one server and a two-module lib with a single consumer; `code/lib` was only ever "vendored" because the monorepo's path hack needed a home. Folding `validators`/`logconfig` in as ordinary modules gives the same end state (no path hacks, real imports) without a second distribution whose only consumer is its sibling. If a second serving component ever appears, the workspace already has the `packages/*` slot for it.
3. Instances are config-only directories, not workspace members — unlike the sibling's instances, these own no code (no discoverers, no console scripts), so a per-instance `pyproject.toml`/`src/`/`tests/` would be empty ceremony. The workspace `members` glob is `packages/*` only. An instance here is: an env file (credentials, tokens, port, instructions), its validation config, and its logs/data. Onboarding a third instance is `mkdir instances/<name>` + copy `.env.example` + grants in the new database's owning repo.
4. Task 4 groups every file move into one task and one working-tree state rather than splitting per file, for two reasons. First, it is one mechanical relocation applied across the tree, with every affected file named in the subtasks. Second, the one-move rule: `git filter-repo` path-carving loses `--follow` history across successive renames — the sibling observed this in the original repo split and codified it (its reorg decision 7) — so all `git mv`s must reach history as a single commit and no later reshuffle may cross the engine/instance boundary. See decision 18 for who commits.
5. Task 5 groups four code files into one task rather than splitting them per file. It is a single mechanical substitution — delete the `sys.path.insert`, repoint the import at the installed package — repeated across near-identical sites, so per-file tasks would obscure that it is one decision applied four times. Every affected file is named in the task header and subtasks.
6. Ambient credentials removed — dropping the `.env.mcp.policy_db` fallback (task 7.1) mirrors the sibling's removal of the default dotenv search (its reorg decisions 2-3): with instances explicit, there is nothing correct for a default to find, and the current fallback means a flag-less launch silently serves policy_db. A forgotten flag must be a loud error, not a silent serve. The `repo_root` anchoring removal (7.2) is forced regardless: an installed console script's `__file__` lives in the venv, so `parents[2]` resolves to garbage; absolute paths or repo-root invocation become the documented norm.
7. Instance-name and log anchoring — once every instance's env file is named `.env`, the file stem is useless as an instance-name default, so the parent directory name takes over (task 7.3); both real env files set `MCP_INSTANCE_NAME` explicitly today, so behavior is unchanged in practice. Logs anchor to the env file's instance directory (task 7.4) — the sibling's convention — so an installed entry point run from any directory stops scattering CWD-relative `logs/` trees. The validation script gets the same treatment (9.2); it currently writes to a CWD-relative `logs/mcp_db_server/data_validation`, which is also the wrong tree now that the script is not part of the server's log namespace.
8. Contract replacement — the dual-copy `corpus-schema-contract.md` scheme is already dead (the sibling binned its copy; its live content moved into MAINTAINING.packages.md §3, deliberately path-free). This activity gives the read side the matching treatment: MAINTAINING.server.md's "data interface the server reads" section (task 11.2) states what this server requires of any corpus it serves, each repo owning its half of the interface in its own current-truth doc, kept free of this repo's file paths so restructures cannot stale it (the sibling's stated rule for its half). The one rule that must not be lost in the move: embedding-model identity — the dimension guard catches only dimension mismatches, not a different same-dimension model, so no runtime guard fully enforces it. The source-table shapes the old contract also carried are pipeline-internal and already live only in the sibling. The root pyproject's model-pin comment cites the deleted file and is repointed in task 2.2.
9. No new data outputs, so no per-output validation task is written — this is a restructure, and per the refactor convention what is under test is behavioral: the full suite passing from any working directory (task 14.1), the grep checks proving the old layout is unreferenced (14.2), the smoke launches of both instances (15.1, 15.4), and the search-equivalence identity diff (15.3). No tool behavior, HTTP surface, auth semantics, or search results change. The 2106-line `server.py` is NOT split into modules (orthogonal to layout, and splitting would churn the code-review record mirror); the FastMCP 1.x and model-stack pins are untouched.
10. Data reachability — verified empirically at drafting time, not assumed: `policy_db` answers on `localhost:5432` and reports 5 `vector`-typed columns. The smoke tests and both equivalence captures therefore execute here rather than being documented for manual execution.
