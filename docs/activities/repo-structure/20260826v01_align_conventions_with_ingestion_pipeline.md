3. [completed] Create the shared path helpers module - `packages/mcp_db_server/src/mcp_db_server/paths.py`
   - 3.1. `is_rooted_path(raw: str) -> bool` — true when a path is rooted under either platform's rules (POSIX leading `/`, Windows drive letter or UNC prefix), so a path that is absolute on the other host is rejected rather than silently treated as relative here
   - 3.2. `find_instance_root(start: str | Path) -> Path | None` — walk `start` and its parents for the instance marker, returning `None` when absent.    - 3.5. `resolve_log_dir(subdir, anchor_path=None) -> Path` — instance root when found, else `fallback_log_root() / subdir`; `fallback_log_root()` returns `Path(tempfile.gettempdir()) / "mcp_db_server" / "logs"`. The asymmetry with 3.3 is deliberate (rationale in decision 8)

## Key Data Decisions and Considerations

1. Scope — this activity closes only the gaps the post-reorg comparison against `ingestion_pipeline` actually found. It changes no tool behavior, no HTTP surface, no auth semantics, and no search results; the one user-visible change is the CLI flag rename in decision 9.
2. The virtualenv must leave iCloud's reach. This repo sits under an iCloud-synced `~/Documents`, and `brctl status` confirms the daemon actively syncing `.venv/lib/python3.14/site-packages/`. The sibling's `.gitignore` documents the failure mode — "duplicated `lib 2/` directories, hidden `.pth` files that CPython then ignores... `uv sync` does not repair the damage" — and its workspace activity's note 20 records the same corruption independently. This repo hit it during the reorg: minutes after the restructure commit, the whole suite failed with `ModuleNotFoundError: No module named 'mcp_db_server'` against a venv half-migrated to Python 3.14 with stale console scripts, while `uv sync` reported "Audited 72 packages" and did nothing. Deleting `.venv` and re-syncing was the only fix. `.venv.nosync` with a `.venv` symlink prevents recurrence because iCloud skips paths ending `.nosync`.
3. The ignore rule for credentials is weaker than the layout it now protects. The reorg replaced the old `.env.mcp.*` pair with `!.env.example`, leaving only the bare `.env` pattern, which matches that exact name and nothing else. Verified by `git check-ignore`: `.env.backup`, `.env.local`, `instances/policy_db/.env.bak`, and the retired `.env.mcp.policy_db` are all committable today. The real files are safe because they are named `.env`, so this is a latent hazard rather than a live exposure — but the sibling's `.env*` plus re-inclusions costs nothing and removes the class.
4. Explicit `instances/*/logs/` and `instances/*/data/` replace the bare patterns because a no-slash `logs/` or `data/` matches at any depth, so any future `docs/data/` or a package fixture directory would be silently untrackable. The sibling states this reason in its own file. The stale repo-root `logs/` tree is a leftover from the pre-reorg baseline capture under the old CWD-relative logging and has no writer under the new layout.
5. Reviews move with their code but are never rewritten. The sibling's `MAINTAINING.packages.md` §7 defines `docs/code_review/` as "per-file reviews, mirroring the source tree", and its workspace activity's decision 12 states the split plainly: "Review files move with the code but are not rewritten. A review records what its reviewer saw at the time, including the source paths it cites; the directory says where the file is now." Its commit `ea0585a` moved 104 review files for exactly this reason, noting that otherwise "a fresh review of those same files would have landed elsewhere again" — the drift this repo has now, with reviews under `docs/code_review/mcp_db_server/` mirroring a `code/` tree that no longer exists.
6. The prior activity's decision 16 is corrected by appending, not editing. It claimed the sibling's policy is to leave reviews in place, citing "append new records, never rewrite old ones to match the present" — the content half of the rule, applied to location. Since that same policy forbids rewriting dated records, the correction is recorded as a new numbered implementation note on the prior activity (the sibling's own convention, which continues numbering under an `### Implementation notes` subheading) rather than by editing decision 16 in place.
7. Instance-root discovery walks to a marker rather than counting levels, but the marker differs from the sibling's. The sibling walks up for a `pyproject.toml`, which works because its instances are workspace members with code. This repo's instances are config-only by the reorg's decision 3, so no `pyproject.toml` exists to find, and the current helpers instead assume position — the env file's parent is the instance root, the config's parent-of-`config/` is the instance root. That is precisely the level-counting the sibling's workspace activity decision 8 rejected. The marker adopted here is the presence of `.env` or `.env.example` alone — the strongest signal a code-free instance can offer, and the defining property of an instance under the prior activity's decision 3. A stricter conjunction requiring `config/` or `logs/` alongside was considered and rejected because it fails `instances/metadata_db/`, which has no `config/` at all and whose `logs/` does not exist until the first run creates it — the marker would depend on the directory the run is trying to place. If instances ever gain code and a `pyproject.toml`, the marker should switch to match the sibling exactly.
   Note the walk is only load-bearing for the config-path case: on the server path `env_path.parent` is the instance root by construction, so `resolve_log_dir` is passed an anchor it can trust.
8. The two anchors fail differently on purpose, following the sibling. A config path with no resolvable instance root raises and aborts the run, because guessing where a data file belongs risks reading or writing the wrong corpus. A log directory with no resolvable root falls back to a temp path, because losing logs should never abort a run that is otherwise valid. The sibling implements this same asymmetry.
9. The CLI rename is the only breaking change here, and it is the one item worth reconsidering. The sibling's flag is `--env-file`, declared `required=True`, so argparse itself produces the usage error and exit 2; this repo chose `--env` with a hand-rolled check that exits 1. Aligning gains cross-repo muscle memory and standard exit semantics, and costs a rename in every documented command (task 11) plus any operator's shell history and service unit. If the churn is judged not worth it, drop tasks 6.1-6.3, 7.1-7.2, 11.1, and 13.2 and keep the rest of the activity — nothing else depends on the flag's spelling.
   The sibling reaches `required=True` cleanly only because it has no env-var path at all ("nothing reads an env-file path from the environment"). This repo does, and `required=True` cannot express it: argparse evaluates `required` against the flag's presence on the command line and ignores any default, so declaring both would reject a correctly-set `MCP_ENV_FILE`. Task 6.2 therefore leaves the flag optional and calls `parser.error(...)` when neither source supplies a path, which prints the same usage block and exits 2 — the sibling's observable behavior, with `MCP_ENV_FILE` retained. Retiring `MCP_ENV_FILE` to match the sibling exactly was considered and rejected: it is a second breaking change, and the env-var path is how a service manager supplies the file without rewriting its command line.
10. The portability guard is enforced by a test rather than by prose, following the sibling, because a convention documented only in a maintaining file is one new file away from being violated. `Path.is_absolute()` answers for the running host only, so a config value like `C:\corpus\out.json` is "relative" on macOS and would be silently resolved under the instance root. There is one such call today, at `data_val_search_equivalence.py:267`.
11. The shipped-config guards derive their expectations rather than restating them, because a guard whose expected set is hardcoded drifts in exactly the way the guard exists to catch. The sibling can compare an example against its `validate_config` function; this repo has no such authority — the server reads configuration through scattered `os.environ.get(...)` calls with inline defaults. What it does have is a sharp subset: five variables read by direct `os.environ[...]` subscript, which raise `KeyError` when absent and are therefore the hard requirements. Task 9.1 extracts those from the AST, so adding a sixth subscript automatically tightens the guard. The optional variables are deliberately left unchecked; a fuller contract would need a config-validation function the server does not have, and building one is a separate activity.
    These tests also locate the repo by marker, not by CWD, because pytest's rootdir differs by invocation directory — a lesson this repo already hit: a bare `uv run pytest` from `instances/policy_db/` collects zero tests because `testpaths` is rootdir-relative. A guard test resolving its fixtures from the CWD would silently pass by finding nothing.
