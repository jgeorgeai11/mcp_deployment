## Key Data Decisions and Considerations

1. KEEP the retrieval core: hybrid dense (pgvector cosine) + sparse (Postgres FTS) fused with RRF is current best practice (RRF specifically avoids the cosine-vs-keyword score-normalization pitfall). Only the server framework, the reranking stage, and the query-model resolution change.
2. FastMCP, stateless streamable HTTP (`stateless_http=True`, `json_response=True`) — the 2026-recommended way to build/deploy a Python MCP server; deletes ~300 lines of hand-rolled transport/session code and makes tools declarative. The low-level SDK is recommended only for non-standard transports, which this server does not need.
3. Model consistency — MANUAL (env + guard), NOT the table-COMMENT mechanism. Set the query model per instance via `MCP_EMBEDDING_MODEL`, and FIX the code default from `gte-large` (1024-dim) to the granite model (384-dim) so the fallback already matches the embeddings. Add a search-time DIMENSION GUARD (loaded-model dim vs the table's `vector(N)` dim) that fails clearly on mismatch. Sufficient because the system uses ONE model (granite) across all embeddings, and per-instance scoping means each server serves one coherent dataset. The self-correcting table-COMMENT mechanism (deferred #10) is intentionally NOT built — revisit only if a single instance must serve tables embedded with DIFFERENT models. Tradeoff: the guard catches DIMENSION mismatches loudly but not same-dimension-different-model (silent mis-ranking) — acceptable while one model is used everywhere.
4. Reranking pipeline: hybrid+RRF becomes the CANDIDATE generator (top ~50), a cross-encoder reranks to top-k. Rerank only the shortlist, so the cross-encoder runs on ~50 (query, chunk) pairs per search — feasible on the CPU-only VM (~200-400ms added latency).
5. Reranker model — DECIDED `Ettin-reranker-150M`, but IMPLEMENTED with `BAAI/bge-reranker-base` (the listed fallback). At build time `cross-encoder/ettin-reranker-150m-v1` (the real HF id, confirmed to exist) FAILS to load under transformers 4.57.6 / sentence-transformers 5.2.2 — its repo declares an unavailable tokenizer class (`TokenizersBackend`), even with `trust_remote_code`. `BAAI/bge-reranker-base` (~278M) loads cleanly, scores correctly, and is CPU-feasible for the ~50-candidate shortlist; it's the `_DEFAULT_RERANK_MODEL` constant (overridable via `MCP_RERANK_MODEL`). Revisit Ettin if a future transformers/the repo fixes the tokenizer config. Cross-encoder reranking adds ~+5 to +15 NDCG@10. Loaded via `sentence_transformers.CrossEncoder`.
6. Auth — DECIDED: Model B (one shared server on the VM, reached from workstations over the network), so auth is REQUIRED. Use per-user bearer tokens (`MCP_AUTH_TOKENS`, a set of `label:token` pairs) so individual users are revocable/attributable — simpler than OAuth, which is overkill for a small trusted team. TRANSPORT SECURITY (Notes 2/6): bind instances to `127.0.0.1` (task 3.8) behind a reverse proxy that terminates TLS on `:443` and routes per instance — otherwise the token + results are sniffable on the wire. TLS is an ops follow-up, not code in this activity.
7. BM25 DESCOPED (infra-blocked): the Postgres (15.15) exposes only the `vector` extension — no `pg_search`/ParadeDB/`vchord_bm25`/`rum`. True BM25 needs a ParadeDB-based Postgres or a built `pg_search`, an infra change, not code. The sparse leg stays `ts_rank_cd`. Revisit if/when the deployment DB supports it.
8. The six tools' public contract and the timeout/row-limit/single-statement safety posture are preserved through the rewrite — a re-platforming + enhancement (the database allow-list becomes role-derived, a tightening). TWO intentional return-shape changes: `search` results gain a `rerank_score`; `run_sql` now returns `{rows, row_count, truncated}` instead of a bare `list[dict]` so the truncation flag is visible to the caller (previously only logged). The read-only guarantee, previously only NOMINAL (server ran as a superuser), is now REAL via task 1's dedicated role.
9. Multi-server / instance-scoping driven by the Postgres ROLE (single source of truth — NOT an app-level DB list): the SAME codebase runs as several scoped deployments. Each instance's scoped read-only role can `CONNECT` to only the databases it should serve; the server DERIVES its served set from the role's grants (`has_database_privilege ... 'CONNECT'`), so there is no `MCP_DATABASES` config to drift from the grants. Isolation is by DEPLOYMENT — separate process + scoped role + token set + port per instance — stronger than authorization-only scoping: a compromised instance's role cannot connect to databases outside its grants. The module is renamed and flattened `code/mcp_servers/mcp_all_db` -> `code/mcp_db_server` (generic, matching the flat sibling modules) in task 3.1; the "policy_db" identity lives on the INSTANCE (its env `.env.mcp.policy_db`, role `mcp_ro_policy`, `MCP_INSTANCE_NAME`), not the module. All three list tools are privilege-filtered consistently (tasks 3.6/3.7). The grants are the hard DATA boundary; the residual is that `run_sql` can still enumerate object NAMES from the world-readable catalogs (names, not contents) — acceptable for an internal deployment, fully closed only by separate clusters.
