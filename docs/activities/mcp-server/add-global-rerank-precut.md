---
name: add-global-rerank-precut
goal: Decouple MCP `search` latency from the number of schemas/tables searched by capping the candidate pool that reaches the cross-encoder reranker. Today each (schema, table) contributes `MCP_RERANK_POOL` (default 50) candidates and ALL of them are reranked, so a 3-schema call reranks ~150 candidates (~3x a single-schema call). This adds a cheap global pre-cut: after merging candidates across all schemas/tables, sort by the existing RRF `fused_score` and keep only the top N globally before reranking, so a multi-schema call reranks ~50 candidates like a single-table call. Backward-compatible: with the default cap, a search touching a single embedding table is unchanged; searches touching multiple tables (multi-schema, or a single multi-table schema like qpp_cm) are trimmed to the cap.
created: 2026-07-01
updated: 2026-07-01

## Key Data Decisions and Considerations

1. Pre-cut on RRF `fused_score`, not raw similarity - `reciprocal_rank_fusion` (line 876) scores a row as the sum over the legs it appears in of `1/(k + rank)` with `k=60` and NO per-leg normalization. Rank-based fusion means cosine distance and `ts_rank_cd` (incomparable raw scales) need no calibration, but it also means the score depends on how many legs a row matched: a dual-leg (dense AND sparse) match tops out near `2/61`, a single-leg match near `1/61`. This is only a fair GLOBAL sort key because of an invariant that must hold for it to be sound: **every served embedding table is hybrid** - `generate_embeddings.py` (line 298) unconditionally adds a `chunk_tsv tsvector generated always as (...) stored` column and GIN index to every embedding table, so every table feeds both legs to RRF and its candidates live on the same `fused_score` scale. Under that invariant the cross-table comparison is fair, and the residual structure - dual-leg (multi-signal-agreement) rows outranking single-leg rows - is intended, not a bias: a chunk matching both keyword and semantic search is a stronger candidate. ASSUMPTION/GUARD: this relies on the all-hybrid invariant. A dense-only embedding table (never produced by the standard pipeline, but possible if one were hand-created and served) can only produce single-leg rows capped near `1/61`, so its candidates could be under-represented in the global pool relative to dual-leg rows from hybrid tables. Task 2.6 pins this behavior with a test; if mixed hybrid/dense-only tables ever become a real serving pattern, switch the selection to per-table-normalized `fused_score` or round-robin-by-within-table-rank instead of a raw global sort. A minor, benign effect under the invariant: exact `fused_score` ties across tables (same leg-count at the same rank) break by candidate iteration order via Python's stable sort - acceptable, since tied rows are equally good by the fusion metric and the reranker makes the final call.
2. Global cap = `max(top_k, MCP_RERANK_GLOBAL_POOL)` - the reranker pool must never be smaller than the number of results being returned, mirroring the existing `pool_size = max(top_k, _rerank_pool())` guard, or a large `top_k` would be starved by a small cap.
3. Default cap = `MCP_RERANK_POOL` (50) - the pre-cut fires on candidate COUNT (`len(candidates) > cap`), i.e. on the number of TABLES touched, not the number of schemas. With the default, a search that touches a SINGLE embedding table (~50 candidates) is a no-op and byte-for-byte unchanged. It is NOT a no-op for a search that touches multiple tables - including a single-schema search over a multi-table schema: `cms_iom` and `usc` each have one embedding table (`document_content_embedding`), but `qpp_cm` has two (`sheet_content_embedding` + `document_content_embedding`), so a single-schema `qpp_cm` search produces ~100 candidates and IS trimmed to 50 (behavior can change vs. pre-pre-cut). That is the intended cost-bounding behavior; it just is not accurately described as "single-schema is always unchanged." One number (`MCP_RERANK_POOL`) governs both per-table depth and the global default, so there is a single dial to reason about; `MCP_RERANK_GLOBAL_POOL` lets an instance decouple them if needed.
4. Recall trade-off is bounded and tunable - the dropped candidates are each table's lowest-`fused_score` rows, the least likely to survive reranking anyway, and the default keeps a 5x buffer over a typical `top_k` of ~10. The residual risk is a chunk with a weak hybrid score but strong cross-encoder relevance being trimmed pre-rerank; `MCP_RERANK_GLOBAL_POOL` can be raised (up to effectively disabling the cut) if a query set ever shows recall loss. Task 4.3 checks this against an uncapped baseline.
5. Correct cross-schema behavior, not just cheaper - after the cut a schema with genuinely stronger matches can occupy more of the global pool than its "1/N share" (e.g. 22/19/9 across three schemas), which is the more accurate cross-schema ranking, whereas today's fixed per-table 50 gives every table equal pool weight regardless of match quality.
6. Placement - the pre-cut goes after the merged-pool build and the `if not candidates: return []` guard, and before the reranker `pairs`/`predict` block; the downstream `candidates.sort(key=rerank_score)` and `candidates[:top_k]` are unchanged.
7. Rejected alternatives for the single-leg risk - (a) restricting search to hybrid-only tables was rejected: it removes the supported dense-only fallback even for single-schema searches (where there is no pre-cut and no bias) and fails silently. (b) Broadening `_discover_embedding_tables` to also find sparse-only (tsvector, no vector) tables was rejected: the pipeline never produces such tables (`generate_embeddings.py` always makes hybrid tables), it flips the intentional dense-primary architecture, and it is a larger standalone change (discovery + the "no vector column" searchable contract + dimension guard + dense-leg fallback). Both are out of scope; the chosen handling is: keep raw global `fused_score` selection (correct for the all-hybrid tables actually served) + the structural (table-shape) tripwire (1.3b), which flags a served dense-only table without false-firing on the normal case of a schema having no strong matches + the guard test (2.6), with per-table normalization / round-robin named as the fix only if dense-only tables ever become a real serving pattern.
8. Out of scope - parallelizing the per-table DB legs (a separate, complementary latency lever), ONNX/GPU reranker acceleration, and changing `MCP_RERANK_POOL` semantics (per-table depth stays as is). Concurrency throughput of concurrent searches is CPU-bound on the reranker and is not addressed here; this activity reduces per-call rerank work, which also lightens concurrent load, but does not add an inference queue/semaphore.
