## Key Data Decisions and Considerations

1. **The current classification is deliberate, defensible for one case, and wrong for two — which is why this is a reversal rather than a patch.** `test_paths.py` explicitly asserts `C:relative.json` is not rooted and says so in its docstring, so the drive-relative form was considered and classified, not overlooked. That classification is CORRECT in the case it was presumably reasoned about: on Windows, `PureWindowsPath('C:/repo/instances/policy_db') / 'C:relative.json'` is `C:\repo\instances\policy_db\relative.json` — the drive matches the anchor's drive, so the value joins sanely and behaves exactly like a relative path. It fails in the two cases it does not cover, both verified 2026-08-26: `D:data/out.json` joins to `D:data\out.json`, leaving the instance root entirely for another drive's working directory, and `\etc\passwd` joins to `C:\etc\passwd`, leaving it for the drive root. Neither is absolute under either platform's `is_absolute()`, so neither is caught anywhere else. Treating all three as rooted costs the same-drive convenience — a form no config in this repo uses — and closes both escapes with one expression.
2. **Adopt the sibling's formulation rather than extending the regexes.** `PureWindowsPath(raw).drive or PureWindowsPath(raw).root or PurePosixPath(raw).root` is three attribute reads that delegate every platform rule to `pathlib`, where the regexes must re-encode each rule and were already two short. It is the exact expression now in `ingpipe_lib.paths.is_rooted_path`, verified there against this same case list, so the two repos answer identically for any value a shared corpus config could carry — which matters because a path written on one side is read by a maintainer on the other.
3. **The log timestamp fix is about reading two repos' logs together.** Naive local time is a defect in isolation — the sibling recorded it as such — but the reason to carry the fix here rather than leave the copy as it is: `ingestion_pipeline` writes the corpus and `mcp_deployment` serves it, and diagnosing "the server returns nothing for this document" means reading an ingest log against a server log. With one side UTC and the other local, the two cannot be ordered, and the mismatch is invisible in the files themselves because neither form carries a zone. The `Z` marker is what stops an older local-time value being read as UTC after this lands — and under the canonical append default the two forms genuinely meet inside one file, the first post-fix run appending UTC records after the last pre-fix run's local-time ones. (History of this point: the 2026-08-26 draft claimed the coexistence under the then-current truncate default, which was wrong and was corrected; the 2026-08-27 full adoption of the canonical append default makes the claim true.)
4. **This activity writes no data file or table, so it carries no data-validation tasks.** Every change is to two library modules, their tests, and one maintaining file. What is under test is the suite and static analysis (task 6), plus the two predicate cases that now change classification (subtasks 2.1 and 2.2).
5. **Scope is deliberately these two gaps, not a re-audit of the alignment activity.** The rest of that activity's work was checked on 2026-08-26 and is sound: `test_conventions.py` parses with `ast` rather than grepping (stronger than the sibling's equivalent), `PLW1514` carries the `preview` + `explicit-preview-rules` gating the sibling independently arrived at, `test_shipped_configs.py` guards the example configs, and the data-interface section correctly mirrors the sibling's §3 while staying free of file paths in either repo. Nothing else surfaced.
6. **Full adoption of the 2026-08-27 logging skill, chosen over a timestamps-only fix.** The python-development skill's canonical logconfig moved past this repo's fork in the same morning sync that this activity was already tracking for UTC: it now specifies the exact `asctime` shape (UTC ISO-8601 with milliseconds, readable by `datetime.fromisoformat` — a `.jsonl` log is read by machines), flips the `overwrite` default to append, adds 10 MiB / 3-backup rotation, and scopes the already-configured check to its own named handler so a test runner's capture handlers no longer silently suppress file logging. Adopting it wholesale keeps the fork's divergence at zero and is the reviewed pick-up the skill's own install note prescribes; a timestamps-only fix would have left this repo diverged on the very module the skill exists to standardize. Accepted consequences, deliberately NOT behavior-preserving for log files (server, tool, and search behavior are untouched): per-instance logs accumulate across runs instead of truncating, bounded near 40 MiB per script by rotation; and `setup_logging` now registers under test runners, which task 4.4's foreign-handler test pins. The skill's one-writer-per-file caveat (rotation renames and overwrite deletes, both of which raise on Windows while another process holds the file) is satisfied here: each instance runs one server process and logs under its own instance name.

Nothing in `server.py` filters, parses, or assumes a shape for `collection_path` — it is carried through as an opaque key — so the change passes through this server untouched.

The sibling's fix (`ingestion_pipeline` commit `fabe62f`) detaches foreign `HANDLER_NAME` handlers in the test fixture and restores them after. This repo does not currently have the triggering pattern — verified 2026-08-27 that no test module here calls `setup_logging` at import — but the guard is carried anyway: it is a few lines, it makes the two repos' logconfig test files interchangeable for review, and it means the next import-time call someone adds degrades nothing. This repo's only caller is `resolve_config_path`, which accepts `raw: str | Path` and passes `str(raw)`. For the forms this activity is about the widened predicate classifies both renderings identically — `/etc/passwd` and `\etc\passwd` each carry a root, and a drive is preserved by either rendering — so no rooted value is misclassified by the `str()` path. The caveat still belongs in the docstring: the two repos' predicates should state the same contract, and a future caller holding a `Path` should not have to rediscover why the sibling's Args block says what it says.
