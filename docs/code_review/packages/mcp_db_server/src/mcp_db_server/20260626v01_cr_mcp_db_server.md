## Implementation Plan

1. [completed] Correctness / event-loop safety - `code/mcp_db_server/mcp_db_server.py`
   - 1.1. [completed] Lines 572-1124 (all six `async def` tools) and 366-506, 842-973 (`_search_single_table` + introspection helpers): every tool does **synchronous, blocking** SQLAlchemy I/O (`engine.connect()`, `conn.execute(...)`, `result.fetchall()`) directly inside `async def` bodies. The author correctly offloaded the two CPU/IO-bound model calls (`model.encode`, `reranker.predict`) via `asyncio.to_thread` (lines 1067, 1105) but applied none of that reasoning to the DB calls. With a single uvicorn worker, each query blocks the event loop, so all concurrent requests serialize; worse, `run_sql`'s `set local statement_timeout = '5s'` (line 815) means one slow/pathological query freezes the whole process — **including the `/health` liveness probe** (which shares the loop) — for up to 5 seconds. This is the headline correctness issue for a network-reachable shared server (Model B).
        - Current: `async def run_sql(...)` / `async def search(...)` etc. calling `with engine.connect() as conn: conn.execute(...)` synchronously on the event loop.
        - Expected: either (a) declare the tool functions plain `def` — FastMCP runs sync tools in an anyio worker thread, so the loop stays free (simplest, and the functions are already self-contained); or (b) wrap each DB round-trip in `await asyncio.to_thread(...)`. Option (a) is cleaner and matches the "synchronous so it is safe to call inside the loop" intent already noted for `_fetch_databases` (lines 206-208).
        - Rationale: exception-handling/async correctness; a 5s statement timeout that can stall `/health` defeats the purpose of an open liveness endpoint and serializes a multi-user server.
   - 1.2. [completed] Lines 93-102, 122-173, 230-247, 289-320, 335-358: the lazy global singletons (`_engines`, `_served_databases`, `_embedding_model`, `_reranker`) are unguarded "check-then-set" caches. They are race-safe **today only because** the blocking event loop serializes everything (Finding 1.1). If 1.1 is fixed by moving tools to a threadpool (option a), two concurrent first-calls can both observe `None` and double-load a model / build duplicate engines. Guard the singletons (e.g. a `threading.Lock` around each lazy init) **as part of** the 1.1 fix, not separately.
        - Rationale: the two findings interact; fixing 1.1 without 1.2 trades a serialization bug for a races bug.
   - 1.3. [completed] Lines 230-247 vs 586-589: cache divergence between the served-set paths. `list_databases` calls `_fetch_databases()` **fresh on every call** (line 587), but `_validate_database` (used by every other tool) reads the **process-lifetime cached** `get_served_databases()` (line 262, cache at lines 239-242, never invalidated). After an operator `GRANT CONNECT` on a new DB, a user sees the new database in `list_databases` but gets `"... is not served by this instance"` from `list_schemas(new_db)` / `run_sql(new_db, ...)` until the process is restarted; a revoked DB stays usable via the cached set. The two tools should agree.
        - Current: `list_databases` -> `_fetch_databases()` (uncached); `_validate_database` -> `get_served_databases()` (cached forever).
        - Expected: either route `list_databases` through `get_served_databases()` too (consistent, but then both are stale until restart — acceptable and documented), or give the cache a TTL/invalidation. At minimum document that the served set is fixed at first-use and a grant/revoke needs a restart.

2. [completed] Reranker text-column coupling - `code/mcp_db_server/mcp_db_server.py`
   - 2.1. [completed] Lines 86, 1101-1104: the reranker scores `(query, c.get("chunk_text", "") or "")` against a **hardcoded** `_RERANK_TEXT_COLUMN = "chunk_text"`. `search` auto-discovers **every** table with a vector column (`_discover_embedding_tables`, lines 487-506, 1032), and any such table whose text column is not literally named `chunk_text` feeds the cross-encoder an empty string, silently ranking those rows to the bottom (the `or ""` masks the miss — no error, no log). Verified mitigant: the canonical `generate_embeddings.py` pipeline always materializes the embedded text into a column literally named `chunk_text` (DDL line 295, insert line 622), even when the *source* `embed_columns` is `row_text` (qpp_cm/proposals `sheet_content`). So for tables built by that pipeline this is currently correct — but the assumption is undocumented and brittle: a vector table created by any other path (or the source table itself, if it carries a `vector` column) reranks to garbage with no signal.
        - Current: `_RERANK_TEXT_COLUMN = "chunk_text"`; `[query, str(c.get(_RERANK_TEXT_COLUMN, "") or "")]`.
        - Expected: (a) document the invariant ("reranking assumes the embedded-text column is `chunk_text`, as produced by generate_embeddings.py"), and (b) log a warning (once per table) when a candidate lacks a non-empty `chunk_text` so a misnamed/empty text column is visible rather than silently degrading rank quality. Optionally derive the text column from the table rather than hardcoding.
        - Rationale: data-validation / comments skills — a silent quality regression on an unexpected schema should be loud, not absorbed by `or ""`.

4. [completed] run_sql single-statement heuristic - `code/mcp_db_server/mcp_db_server.py`
   - 4.1. [completed] Lines 799-806: the multi-statement guard is a textual `;` check (`stripped = sql.strip().rstrip(";"); if ";" in stripped: raise`). Two honest limitations worth a code comment: (a) **false positive** — a legitimate single statement containing a semicolon inside a string/identifier literal (e.g. `select ';' as x`) is rejected; (b) it does **not** constrain the statement *kind* — a single `update ... ` / `delete ... ` / `drop ... ` with no semicolon passes this guard untouched. (b) is by design: read-only is enforced 100% by the Postgres `mcp_ro_policy` role, with zero application-layer enforcement (Decision 8 / activity task 1). That is the correct, honest answer to "is read-only truly enforced" — it IS, but solely at the DB grant layer; the `;` heuristic is a multi-statement guard, not a write guard.
        - Current: comment says only "Reject multiple statements"; no note on the literal false-positive or that write-rejection relies entirely on the role.
        - Expected: extend the inline comment to state (i) the role is the sole read-only enforcement and (ii) the `;`-in-literal false-positive is an accepted limitation; consider documenting in the tool docstring that writes are blocked by the connection role, not by parsing.
        - Rationale: comments skill — make the security model explicit at the guard so a future reader does not mistake the `;` check for write protection.

## Skills with No Issues

1. SQL-injection safety (identifier interpolation): No issues found. Every interpolated `schema`/`table`/`column` routes through the canonical `validate_sql_identifier` (re-exported via importlib from `file_ingestion/_utils.py`, lines 58-66, regex `^[a-z_][a-z0-9_]*$`, `fullmatch`): `list_tables`/`describe_table` validate `schema`/`table` (lines 657, 722-723); `search` validates `schema` and every entry of `tables` (lines 1020, 1028-1029, 1044). `_search_single_table` interpolates `schema`/`table`/`embedding_column`/`tsv_column`/`select_csv` — all sourced from those validated names or from the catalog (`_get_vector_columns`/`_get_tsvector_columns`/`_get_table_columns`), not user input. All VALUES are bound parameters (`:schema`, `:table`, `:query`, `:min_similarity`, `:leg_depth`). The reuse of the canonical validator (deleting the third local copy) matches the activity's task 3.4 and the excel/embedding precedent.
2. pgvector literal interpolation: No issues found / adequate. The query embedding is the only value that cannot be bound (the `<=>` operand), and `math.isfinite` over every component (lines 1071-1072) before building `"[...]"` (line 1077) is sufficient: the values are model-generated Python floats post-`.tolist()`, so the only injection-relevant tokens (`inf`/`nan`, which `str()` would emit) are exactly what `isfinite` rejects; no other characters can appear in a float repr. The inline comment (lines 1074-1076) correctly states the rationale.
3. Auth middleware — fail-closed correctness: No issues found. Unset/empty `MCP_AUTH_TOKENS` rejects every `/mcp` request and logs an operator error (lines 1219-1227); missing/malformed scheme -> 401 (lines 1229-1236); unknown token -> 401 (lines 1238-1242). `_match_token` (lines 1156-1172) iterates the full set with `secrets.compare_digest` and **no early return**, so it neither leaks which token matched via timing nor short-circuits — constant-time per the activity task 3.5. Only the matched label (never the token) is logged (line 1244). `parse_auth_tokens` drops malformed pairs safely (lines 1145-1153).
4. Auth path matching: No issues found. `path.startswith(self.mcp_path)` (`/mcp`) is fail-closed-safe: a hypothetical `/mcpx` gets *more* auth, not less, and `streamable_http_path="/mcp"` is the only non-health route. `/health` is correctly left open for liveness (lines 1212-1215). `scope["type"] != "http"` is passed straight through (lines 1205-1207) — see point 9.
5. FastMCP usage (stateless HTTP + lifespan): No issues found. `FastMCP(stateless_http=True, json_response=True, streamable_http_path="/mcp")` (lines 1283-1288) matches activity task 3.2. Tools are registered via `mcp.tool()(fn)` returning the function unchanged, so the core `async def`s stay directly unit-testable (the conftest relies on this). Wrapping `mcp.streamable_http_app()` in `BearerAuthMiddleware` does **NOT** break the session manager: the middleware forwards the `lifespan` scope untouched (`scope["type"] != "http"` branch, lines 1205-1207), so the streamable-HTTP app's lifespan/session-manager startup still runs. `/health` is added via `@mcp.custom_route` (lines 1297-1307), the supported FastMCP mechanism.
